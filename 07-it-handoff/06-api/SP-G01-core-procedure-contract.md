# CMMS 2.0 — SP-G01 Core Stored Procedure Contract

**Date:** 2026-10-08  
**Target:** db-omm-dev / schema cmms  
**Status:** DESIGN_READY_FOR_RUNTIME_VALIDATION

## Purpose

Define the only supported write/read boundary for Power Automate over the DB-G01 CMMS core.

Power Apps does not write CMMS core tables directly.

## Invocation model

```text
Power Apps
   ↓
Power Automate
   ↓
cmms.usp_*
   ↓
cmms tables
```

## Common input contract

Commands accept one parameter:

```sql
@RequestJson nvarchar(max)
```

Every command request should include:

- `requestId` — GUID generated by caller for idempotency;
- `actor` — user/service identity;
- operation-specific fields.

Example:

```json
{
  "requestId": "3f6e8bde-9d97-4c5f-b237-0a2e29a1d6be",
  "actor": "user@company.com",
  "maintenanceOccurrenceId": 123
}
```

## Common output contract

Every procedure returns exactly one result set with:

- `ReadState`: `READY` or `ERROR`;
- `ResultJson`: JSON payload, nullable on error;
- `ErrorCode`: blank on success, otherwise controlled code;
- `ErrorMessage`: blank on success, otherwise controlled message.

## Error catalog

| Code | Meaning |
|---|---|
| CMMS-400 | Invalid/missing request data |
| CMMS-404 | Referenced entity not found |
| CMMS-409 | Business-state conflict / duplicate / invalid transition |
| CMMS-412 | Preconditions/readiness not satisfied |
| CMMS-422 | Domain validation failed |
| CMMS-500 | Unexpected SQL/runtime error |

SQL Server error details may be included in ErrorMessage for dev diagnostics but callers must branch on ErrorCode, not raw SQL message text.

## Idempotency

Command procedures use `cmms.CommandReceipt`.

Unique key: `RequestId`.

If the same requestId is retried:

- the original successful ResultJson is returned;
- no second write is performed.

Natural/filtered unique constraints remain the final database safety net.

## Concurrency

- commands run in explicit transactions;
- rows that control state transitions are read with `UPDLOCK, HOLDLOCK`;
- `CommandReceipt` serializes duplicate requestIds;
- unique indexes protect occurrence/WO/current-schedule invariants.

## State ownership

- Triggering creates/releases `MaintenanceOccurrence`.
- Materialization creates WorkOrder in `PLANNING`.
- Planning sets readiness.
- Scheduling creates current schedule revision/assignment.
- Execution controls actual timestamps/results.
- Technical close validates execution evidence and updates TriggerState for LAST_COMPLETION.

## Important rules

1. Schedule changes never rewrite MaintenanceOccurrence.DueAt.
2. WorkOrder materialization is idempotent by both requestId and unique occurrence index.
3. Execution start cannot occur before the WO is released to execution.
4. Execution complete requires IN_PROGRESS and valid finish >= start.
5. Technical close requires EXECUTION_COMPLETE and validated execution data.
6. LAST_COMPLETION feeds TriggerState.LastCompletionAt from accepted ActualFinishAt.
7. Procedures do not create database users or roles.
